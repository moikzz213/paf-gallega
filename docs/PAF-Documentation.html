1Introduction

What PAF is, what it does, and what it is built with.

1.1 Purpose

PAF (Payment Approval Flow) is an internal web platform that standardises how invoice payments are requested, approved and executed. Employees submit a payment request against a vendor invoice, attach the supporting documents (invoice copy, purchase order, delivery note…), and the platform routes the request through an amount-based, multi-level approval chain. Once fully approved, the finance team schedules and executes the payment, closing the loop with a payment reference. Every step — from creation to payment — is recorded in an immutable audit trail, and the whole portfolio is observable through dashboards, filterable reports and Excel exports.

2System Architecture

A single Laravel application serving a Vue SPA and a session-authenticated JSON API.

2.1 High-level design

PAF is deliberately a single deployable: one Laravel application serves both the compiled Vue single-page application and the JSON API it consumes. There is no separate API host, no token infrastructure and no CORS surface.

Figure 1 — Deployment shape: one Laravel app serves the SPA shell, the JSON API, the database and private file storage.
  • SPA catch-all: Route::view('/{any?}', 'app')->where('any', '^(?!api).*$') returns resources/views/app.blade.php for every non-/api path. The Blade shell carries the CSRF meta tag and the Vite-built bundle; vue-router takes over client-side.
  • API prefix inside web.php: all 31 API routes live under Route::prefix('api') in routes/web.php — there is no routes/api.php. This keeps them inside the web middleware group: database-backed sessions, cookies and CSRF protection apply to every call.
  • JSON errors everywhere: bootstrap/app.php registers $exceptions->shouldRenderJsonWhen(fn ($request) => $request->is('api/*')), so validation failures, auth failures and 404s on /api/* always render as JSON — the SPA never receives an HTML error page or redirect.
  • Role gate: a single custom middleware, EnsureRole (alias role), guards the finance (role:finance,admin) and administration (role:admin) route groups with a strict role whitelist; everything else authorises inside controllers/services.
  • Business logic placement: the approval state machine is isolated in App\Services\ApprovalService (submit / approve / reject, all transactional), and audit writing in App\Services\AuditLogger. Controllers stay thin: validation, authorisation, orchestration.

2.2 Authentication & sessions

  • Classic Laravel session authentication (web guard) — no Sanctum tokens, no JWT. The SPA is same-origin, so the session cookie authenticates every API call transparently.
  • POST /api/login validates credentials with Auth::attempt() (optional remember flag), rejects deactivated accounts (is_active = false) even with a correct password, regenerates the session ID against fixation, and writes a login audit entry. The route is throttled at 10 attempts per minute.
  • POST /api/logout logs the audit entry, logs out the web guard, invalidates the session and regenerates the CSRF token.
  • CSRF: Laravel issues the XSRF-TOKEN cookie, which axios echoes automatically as X-XSRF-TOKEN; the Blade shell's <meta name="csrf-token"> is wired as a fallback X-CSRF-TOKEN header for the first request after a full page load.
  • Sessions, cache and queues are all database-backed (SESSION_DRIVER=database, CACHE_STORE=database, QUEUE_CONNECTION=database) — no Redis dependency.

3Roles & Permissions

Four roles cover the whole payment flow; approvers additionally carry a numeric level.

3.3 Data visibility rules

Visibility is enforced in one Eloquent scope, Invoice::visibleTo($user), applied to lists, dashboards and reports alike:

  1. Admin & finance (canViewAllInvoices()) — unrestricted.
  2. Approver — requests they submitted, plus any request having an approval row at their level, whatever that row's status — including requests they already acted on. Because resubmission rebuilds the chain rows (§4.3), this visibility lasts only until the request is resubmitted with a chain that no longer includes their level.
  3. Requester (and any other role) — only requests where submitted_by is the user.

The same three-way rule is re-implemented for single-record access in InvoiceController::authorizeView() and DocumentController::authorizeAccess() — see §11 for the maintenance note.

4.1 Submitting a payment request

Payment Requests → New Request opens the submission form. Every request receives a unique reference PAF-YYYY-NNNNN (year-scoped, sequential, zero-padded to five digits — e.g. PAF-2026-00061). The requester can Save as Draft (no workflow yet) or Submit for Approval (drafting and submitting in one step).

Drafts (and rejected requests) remain fully editable by their owner; editing records an updated audit entry with the old and new values. Only drafts can be deleted; drafts and pending requests can be cancelled.

4.2 Supporting documents

  • Limits: up to 10 files per request, 10 MB (10,240 KB) each.
  • Accepted types: pdf, jpg, jpeg, png, webp, doc, docx, xls, xlsx, csv, txt (content-sniffed by Laravel's mimes rule, not just the extension).
  • Storage: private local disk under invoices/{invoice_id}/ with a random hashed filename; the original filename is preserved in the database and restored on download.
  • Access control: downloading goes through GET /api/documents/{id}/download which applies the request-visibility rule (§3.3) before streaming the file with its original name.
  • Removal: only the uploader (or an admin) may delete a document, and only while the request is editable (draft/rejected). Uploads and deletions are audit-logged; downloads are not.
  • Documents can be added when creating, and more can be appended when editing an editable request.

4.3 Approval workflow

Routing by amount

Approval levels live in the approval_levels table and are managed from the admin UI. A request must pass every active level whose min_amount ≤ the request's total, in ascending level order (ApprovalLevel::requiredFor()). With the seeded configuration:

Total (AED)Chain
< 10,000L1 Department Manager
10,000 – 49,999.99L1 Department Manager → L2 Finance Director
≥ 50,000L1 Department Manager → L2 Finance Director → L3 CFO

Thresholds are inclusive: a request of exactly 10,000 requires L2. Levels are matched purely on amount — there is no category- or department-based routing.

Chain mechanics

  1. Submit (drafts and rejected requests only): one invoice_approvals row is created per required level (snapshotting the level's name), the request becomes pending_approval with current_level at the lowest level, submitted_at is stamped, and any previous approval/rejection timestamps are cleared. Resubmission starts a fresh cycle: all prior approval rows are deleted first (the audit log keeps the history).
  2. Who may act: an approver whose approval_level equals the request's current_level, or any admin (at any level). Everyone else receives 403; acting on a non-pending request returns a validation error. Levels have no named assignee — any qualified approver at the level may act, first action wins.
  3. Approve: the current level's row is stamped (approver, optional comment, timestamp). If a higher pending level remains, current_level advances to it; otherwise the request becomes approved with approved_at set and enters the finance queue.
  4. Reject: requires a reason (max 2,000 chars). The current level's row is marked rejected, the request becomes rejected with the reason stored on the request itself. The owner may edit and resubmit — restarting the whole chain.
  5. All three operations run inside database transactions and write audit entries.

Approval queue

Approvals (approvers/admins) lists requests pending at the caller's level (admins: all levels), ordered urgent → high → normal → low, then oldest submission first. Approve/reject can be done inline from the queue or from the request detail page, which shows the full approval chain timeline with per-level status, actor, timestamp and comments.

4.4 Payment processing

The Payments workspace (finance/admin) has three tabs backed by GET /api/payments/queue:

  • To Schedule — fully-approved requests, priority-ordered then oldest-approved first. Actions: Schedule (choose a payment date, today or later) or Mark Paid directly.
  • Scheduled — requests with a planned scheduled_date. Action: Mark Paid.
  • Paid — executed payments, most recent first, showing the payment reference.

Mark Paid requires a payment reference (transaction number, max 100 chars); it stamps paid_at (defaults to now, may be supplied) and records the finance user in paid_by. Both actions are audit-logged.

4.6 Dashboard

The landing page adapts to the signed-in user's visibility (§3.3) and refreshes on every visit. It contains:

  • Approval alert (approvers/admins): "N requests are waiting for your approval" with a shortcut to the queue.
  • KPI cards: Total Requests (all time), Pending Approval (count + amount), Awaiting Payment (approved + scheduled, count + amount), Paid This Month (count + amount).
  • Requests by Status — donut of the status distribution, with counts in the legend. Status colors are stable across the entire app (§7.5).
  • Monthly Flow — grouped bars for the last 6 calendar months (including the current one): total submitted vs total paid, in AED.
  • Top Vendors by Spend — top 5 vendors by amount (drafts, cancelled and rejected excluded).
  • Spend by Category — same basis, grouped by category.
  • Recent Requests — the 8 newest visible requests with quick links.

4.7 Reports & Excel export

Reports combines filters (status multi-select, department, category, vendor contains-match, invoice-date range), live summary cards (matching count and amount, plus one card per status in the result), and a paginated result table. All data respects the caller's visibility — a requester exports only their own requests, finance/admin export everything.

Export to Excel downloads paf-invoices-YYYYMMDD-HHMMSS.xlsx with the same filters applied, auto-sized columns and a bold header row. The 23 columns, in order:

Reference No Vendor Invoice No Invoice Date Due Date Currency Amount Tax Total Category Department Cost Center Payment Method Priority Status Requested By Submitted At Approved At Scheduled Date Paid At Payment Reference Paid By Rejection Reason

Amount, Tax and Total are numeric cells; dates are Y-m-d, timestamps Y-m-d H:i; the payment method exports its display label. Every export writes a report_exported audit entry.

4.8 Audit trail

Every state-changing action is written to audit_logs through a single service (AuditLogger::log()), capturing the acting user, the affected request, an action keyword, a human-readable description, the client IP, a timestamp — and, for edits, JSON snapshots of old and new values.

  • Per-request timeline — the request detail page shows its full history chronologically with actor and action icons.
  • Global audit trail (admin) — searchable by text or reference number, filterable by action type (dropdown is populated from the distinct actions actually present), user and date range; 25 entries per page, newest first.

The full catalog of action keywords is in Appendix A.

4.9 Administration

Users

  • Create and edit accounts: name, email (unique), password (min 8; on edit, leave blank to keep), role, department, job title.
  • Choosing the approver role requires an approval level (1–10, picked from the configured levels); the level is cleared automatically when switching to another role.
  • Accounts are never deleted — they are deactivated (is_active), which blocks login with a clear message while preserving history. User changes are audit-logged with before/after snapshots.

Approval levels

  • Levels are rows of level number (1–10, unique) · name · minimum amount · active flag. A minimum of 0 means "reviews every request".
  • Deactivating or deleting a level affects future submissions only — requests already in flight keep the chain they were submitted with (each request snapshots its levels), and past history keeps its records.
  • All changes are audit-logged (approval_level_created/updated/deleted).

6API Reference

31 session-authenticated JSON endpoints under /api, plus the SPA catch-all.

6.1 Conventions

  • Base URL: same origin, prefix /api. All requests need the session cookie; state-changing requests need the CSRF header (handled automatically by the SPA's axios instance).
  • Errors: always JSON on /api/* — 401 {"message":"Unauthenticated."}, 403 with a message, 404, 422 {"message": …, "errors": {field: [msg]}} for validation.
  • Pagination: list endpoints return the standard Laravel paginator (data, total, current_page, per_page, last_page, …); page size via per_page.
  • Invoice updates use POST (POST /api/invoices/{id}) rather than PUT so multipart file uploads work.

6.3 Endpoint details

Invoices

GET /api/invoices

Query params: page, per_page (default 15), mine (bool), status (comma list or array), department, date_from/date_to (on invoice date), q (matches reference, vendor, invoice #), sort (created_at | invoice_date | due_date | total_amount | status, default created_at), dir (asc/desc). Rows include submitter {id, name, department}.

POST /api/invoices  ·  POST /api/invoices/{id}

Multipart body with the fields of §6.4 plus documents[] files and action = draft | submit. Create returns 201 with the invoice (+documents +approvals); update requires owner/admin and draft/rejected status. With action=submit the approval chain is built immediately after saving. Audit: created/updated (+document_uploaded per file, +submitted).

GET /api/invoices/{id}

Full detail: submitter, payer, documents (+uploader), approval chain (+approver names), and the complete audit timeline (+actors). 403 outside the visibility rule.

POST /api/invoices/{id}/submit · /cancel  ·  DELETE /api/invoices/{id}

Owner or admin. Submit: draft/rejected → pending (422 otherwise; 422 if no active levels are configured). Cancel: draft/pending → cancelled. Delete: drafts only. Audit: submitted / cancelled / deleted.

Approvals

GET /api/approvals/pending

Pending requests at the caller's level (admin: every level), ordered urgent→high→normal→low then oldest submitted. 403 for non-approvers.

POST /api/invoices/{id}/approve · /reject

Body: comments — optional ≤2000 on approve, required on reject. Allowed for admins and for approvers whose level equals the request's current_level; otherwise 403. Non-pending requests → 422. Approve advances the chain or finalises; reject terminates with the reason. Audit: approved / rejected.

Payments (finance/admin)

GET /api/payments/queue?status=approved|scheduled|paid

Default approved; other values → 422. Priority-ordered; paid tab newest first.

POST /api/invoices/{id}/schedule · /mark-paid

Schedule: scheduled_date required, today or later; only from approved. Mark paid: payment_reference required ≤100, optional paid_at; from approved or scheduled. Audit: scheduled / paid.

Dashboard, reports, meta

GET /api/dashboard

Returns cards (total, pending, awaiting_payment, paid_this_month — counts and amounts), my_queue, status_distribution, monthly (6 entries: month label, submitted, paid), top_vendors (≤5), by_category, recent (≤8). All scoped by visibility except my_queue, which counts the approver's actual desk.

GET /api/reports  ·  GET /api/reports/export

Filters: status (multi), department, category, vendor (contains), date_from/date_to. Index returns summary (per-status count/amount), totals, and paginated rows (default 25). Export streams the filtered .xlsx (§4.7) and logs report_exported.

GET /api/meta

Dropdown data for the SPA: categories, departments, currencies, payment methods, priorities, statuses, roles, all approval levels (including inactive), and upload limits.

Administration (admin)

GET/POST /api/users  ·  PUT /api/users/{id}

List (search q, filter role), create (201), update. No delete — deactivate via is_active. Audit: user_created / user_updated (with role/level/department/active before-after snapshots).

GET/POST /api/approval-levels  ·  PUT/DELETE /api/approval-levels/{id}

CRUD for the level configuration. Audit: approval_level_created/updated/deleted.

GET /api/audit-logs  ·  GET /api/audit-logs/actions

Filters: q (description or invoice reference), action, user_id, date_from/date_to, per_page (default 25), newest first. /actions returns the distinct action keywords for the filter dropdown.

11Security Notes & Known Limitations

An honest register of design decisions and edges to be aware of.

11.1 Security posture

  • Same-origin session auth with CSRF on every mutating call; login throttled (10/min); session fixation protection; deactivated accounts blocked at login.
  • Server-side authorization on every endpoint: role middleware for finance/admin areas, per-record visibility checks for requests and documents, level-matching for approval actions. UI checks are cosmetic duplicates.
  • Documents live on the private disk and stream only through the permission-checked download endpoint.
  • Passwords bcrypt-hashed (12 rounds); audit rows are write-once (no update path, no updated_at).
  • Approval history is snapshotted per request (level names copied), so renaming/removing levels never rewrites history.

11.2 Known limitations & deliberate trade-offs

ItemDetail & mitigation
Resubmission clears chain rowsSubmitting a rejected request deletes its previous approval rows; the prior cycle survives only in the audit trail. Acceptable for an internal tool; revisit if formal approval history tables are needed.
No separation of duties in paymentsAny finance/admin user can schedule and pay any approved request, including one they submitted. Add an ownership guard if policy requires it.
Create-then-submit is two transactionsPOST /api/invoices with action=submit commits the draft first; if chain building fails (e.g. no active levels) the client gets 422 but the draft exists. Harmless — the draft is visible and resubmittable.
Reference-number racenextReferenceNo() reads the last reference without locking; simultaneous creates could collide, in which case the unique index rejects one insert. Fine at internal volumes.
Draft-deletion audit rows unlinkedThe deleted audit entry stores the reference in text but no invoice_id.
Admin approvals log an empty levelApprove/reject audit text interpolates the actor's level; admins (level-less) produce "Level  approved…". Cosmetic.
Document downloads not audit-loggedUploads/deletions are logged; reads are not. Add logging in DocumentController@download if read-auditing is required.
Unbounded per_pageList endpoints accept any page size. Cap it if the dataset grows large.
Visibility rule in three placesInvoice::visibleTo(), InvoiceController::authorizeView(), DocumentController::authorizeAccess() implement the same rule — keep them in sync when changing visibility policy.
Approver visibility is historicalAn approver sees any request that has a chain row at their level, even after acting or when the request sits at another level. Intentional (context), but worth knowing.
Cancelled requests keep pending rowsCancelling mid-chain leaves untouched pending approval rows attached to a terminal request. No functional impact.
Meta exposes inactive levels/api/meta returns all levels including inactive ones (the admin UI needs them); consumers should filter on is_active where relevant.
Skeleton leftoverstailwindcss deps and database/database.sqlite remain from the Laravel skeleton but are unused (live DB is MySQL).
No email notificationsApprovers learn of pending items from the dashboard alert/queue. Mail hooks are a natural next step (MAIL_MAILER currently log).
